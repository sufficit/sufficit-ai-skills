# Customer WhatsApp voice gateway diagnostics

A phone number reported as unable to receive calls can be a customer WhatsApp/QuePasa session, not a SIP endpoint or a PSTN DID. Once the conversation identifies QuePasa, follow that system. An empty SIP/DID search cannot establish the WhatsApp account's status.

## Identify the right resource

- Separate three things: the agent device's personal WhatsApp integration, a customer's QuePasa session, and the customer's telephony gateway route. `whatsapp_status` and `whatsapp_pair` on the agent device describe/connect that device; they do not inspect an arbitrary customer session. Do not pair, generate QR/codes or create sessions to diagnose an existing number.
- Normalize number presentation with DDI and DDD. Some Brazilian WhatsApp accounts use a canonical JID without the mobile ninth digit. Search the authorized session inventory for both forms and verify the returned WID; do not infer that a number is absent from one spelling, or guess a session token from a phone or context ID. A session's `:device` suffix is a device identifier, not its ordinal position among linked devices.
- Use `quepasa-production` and its authorized session-scoped diagnostic access for a session lookup. When the host provides `/data/support/quepasa-readonly/session-status`, call it with the requested number; it exposes only safe live fields and accepts only its explicitly provisioned number aliases. An out-of-scope result means missing provisioned diagnostic access, not a nonexistent account. Do not inspect its credential/config files.

## Read connection and telephony separately

- Confirm live `GET /api/v5/health`: HTTP 200 alone is insufficient; inspect `success`, `state`, ownership and freshness. A stale SQL/runtime record or an old pre-Kubernetes database is historical evidence, not current production state. The active QuePasa database is the Galera deployment in `quepasa-prod`; do not treat a retired `eveo-data` QuePasa copy as current.
- Inspect calls policy, effective calls processing, VoIP mode and customer context. `Ready` proves the WhatsApp connection, not that calls have a configured SIP destination. An empty session context is a tenant-assignment discrepancy, not proof that no downstream route exists. A route may still be associated by its credential/session linkage and carry its own customer context. Do not conflate QuePasa `voipmode=exclusive` with the Sufficit route's `mode=exclusive`, which identifies the Meta/official provider.
- For a known authorized customer context, read `GET /Gateway/WhatsApp/context/{contextId}` and `GET /Gateway/WhatsApp/Quepasa/states?contextid=...`. For the actual route/session identifier returned, use `GET /Gateway/WhatsApp/diagnostics?sessionid=...`, and when needed `GET /Gateway/WhatsApp/Quepasa/devices?sessionid=...` or `/diagnose?sessionid=...`. Discover these operations in the deployed API. The route session identifier is not automatically the phone or the QuePasa record GUID. Never substitute the QuePasa record GUID into `diagnostics?sessionid=` to test for route existence; first resolve the actual route.
- A gateway-route `403` is an actual permission failure for that route query, not evidence of an absent route or disconnected session. Report successful session checks and refused route checks separately. A generic `Bearer error="insufficient_scope"` header can accompany a business context authorization exception: it does not by itself prove that OAuth scopes are missing. Do not recommend reconnecting, logging in again or renewing credentials for a route `403`; preserve the successful checks and identify the refused operation/context for an authorized operator. A context hint supplied by the provisioned helper is not permission to widen access.
- Only after a successful scoped route lookup finds no match may you report an absent route. If the customer context is unknown, report the connection state and unresolved route separately. Ask only for the intended customer/destination needed to configure it. Do not create a route, reassign the session, re-pair or restart as part of a read-only diagnosis. For a configured route, resolve its destination and inspect call/device evidence before declaring end-to-end reception working.

## Linked-device limit and unpredictable call delivery

- WhatsApp delivers calls to at most four linked (companion) devices besides the primary phone. When the account has more than four, inbound call notifications reach the companions unpredictably: some calls ring only on the phone or on other devices and never reach the QuePasa session, so the PBX never sees them. Messages keep arriving normally, so a working chat does not rule this out.
- Count every non-primary device, including a Meta coexistence device (`<number>:99@hosted`, shown as "Coexistência Meta"). Device numbers are identifiers, not positions: position is the rank among companions in ascending device number.
- `GET /Gateway/WhatsApp/diagnostics?sessionid=...` reports this as the item `quepasa_linked_devices_count` ("Quantidade de dispositivos vinculados"). It is a `Warning` above four, with the device list (calls still arrive, just not reliably); the telephony check-up shows the same item for each QuePasa gateway of the customer. `GET /Gateway/WhatsApp/Quepasa/devices?sessionid=...` returns the raw list and `companions`.
- Typical symptom: calls from some callers reach the PBX while others show "Chamando…" and ring only on the customer's physical phone, with no call event at all in QuePasa for those attempts. Do not explain it as a stale caller cache, codec or SIP route problem while the device count is above four.
- Recommended action, for the customer to perform on the primary phone: unlink devices that are not used (Settings › Linked devices) until at most four companions remain, keeping the QuePasa session. Do not unlink, re-pair or restart anything yourself as part of a diagnosis.
